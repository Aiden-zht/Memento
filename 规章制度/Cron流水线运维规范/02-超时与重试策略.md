# 超时与重试策略

## 1. 超时分层设计

Cron 流水线有**三层超时**，每层必须独立配置：

```
┌─────────────────────────────────────────┐
│ Layer 1: Cron 系统超时 (默认 120s)       │
│ ┌─────────────────────────────────────┐ │
│ │ Layer 2: Wrapper / Shell 超时        │ │
│ │ ┌─────────────────────────────────┐ │ │
│ │ │ Layer 3: 单请求超时 (HTTP/API)   │ │ │
│ │ │                                  │ │ │
│ │ │  curl --max-time 15              │ │ │
│ │ │  httpx.Client(timeout=15)        │ │ │
│ │ └─────────────────────────────────┘ │ │
│ └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

### Layer 1：Cron 系统超时

- **默认值**：120 秒（整个 cron tick 的硬上限）
- **no_agent 模式**：整个 script 的执行时间不能超过 120s
- **LLM-driven 模式**：script 执行 + LLM 处理总时间不能超过 120s

**问题**：LLM-driven 模式下，script 超时后 LLM 根本拿不到脚本输出。而 no_agent 模式下，如果 script 成功但 LLM 处理超时，同样会导致数据丢失。

**解决方案**：
1. 对于复杂 pipeline（如游戏折扣日报），将 script 超时部分和 LLM 处理部分拆分到两个 cron job 中
2. 或者，script 本身负责完整的 pipeline 流程（不依赖 LLM 处理）
3. 对于必须在 LLM 中处理的复杂逻辑，增加 cron 系统超时（如果配置允许）

### Layer 2：Wrapper / Shell 超时

Wrapper 脚本中的外部调用应设置合理的 timeout：
- 可达性探测：`--max-time 5`（5 秒不够就说明代理或服务完全不可用）
- Python 脚本：不在 wrapper 中设置，让 Python 内部管理
- 整个 script 的执行时间由 Layer 1 控制

### Layer 3：单请求超时

每个外部 API 请求必须有独立的超时：
- **Steam API**：15-30 秒/请求（通过代理可能更慢）
- **微信 API**：10-15 秒/请求（国内直连，一般很快）
- **翻译 API**：5-10 秒/请求（不可用时快速失败，不拖累整体）

## 2. 代理超时配置

### 2.1 代理协议选择

| 场景 | 推荐协议 | 原因 |
|------|----------|------|
| curl | `socks5://` | mihomo 的 SOCKS5 监听在 7891 |
| Python httpx | `socks5://` | 直接指定 proxy 参数 |
| Python requests | `socks5h://` | `h` 后缀表示远程 DNS 解析 |
| 环境变量 | `http://` 或 `https://` | 指向 mihomo 的 HTTP 监听端口 7890 |

### 2.2 避免重复代理

**禁止**在 wrapper 和主脚本中同时设置不同协议的代理。

正确做法（二选一）：
1. **主脚本内设置**（推荐）：`cron_digest.py` 内部 `os.environ.setdefault("HTTPS_PROXY", "socks5://127.0.0.1:7891")`
2. **Wrapper 设置**：wrapper 中 `export HTTPS_PROXY=socks5://127.0.0.1:7891`，主脚本不设置

**不要**混合使用：wrapper 设 socks5，主脚本设 http proxy。这会导致请求先走 socks5 再走 http proxy，双重代理拖慢速度。

## 3. 失败降级策略

### 3.1 Pipeline 级降级

```
脚本执行超时/失败
    ↓
检查是否有上一日的有效产出
    ↓
有 → 用上一日数据做校验报告，说明今日失败原因
无 → 输出 "Pipeline 不可用" 通知
```

**关键原则**：
- 即使当日 Pipeline 失败，**也不能静默跳过**——必须产出报告说明原因
- 如果当日用 no_agent 模式，script 输出 "FAILED: 原因" 就是有效输出
- 如果当日用 LLM-driven 模式，LLM 应读取上一日有效产出做对比报告

### 3.2 API 级降级

对于多数据源 pipeline（Steam + Epic），采用**逐源降级**：
1. Steam 超时 → 记录 WARNING，尝试 Epic
2. Epic 超时 → 记录 WARNING，仅发布 Steam 数据
3. 全部超时 → 记录 BLOCKING，通知用户

### 3.3 验证级降级

对于双 Agent 验证（Agent A → Agent B），采用**超时降级**：
1. Agent B 验证超时（60s）→ 跳过 Agent B，直接发布
2. 跳过验证必须在 report 中标记 `{ "validated": false, "reason": "timeout" }`
3. 次日在 KPI 中记录 "验证跳过" 作为质量事件

## 4. Cron 任务超时配置表

| Job | 模式 | 预计耗时 | 超时设置 | 说明 |
|-----|------|----------|----------|------|
| Headroom 异常通知 | no_agent | <5s | 120s（默认） | 简单脚本，无外部依赖 |
| 每日服务器快照 | LLM-driven | 30-60s | 120s（默认） | 脚本快，LLM 格式化邮件 |
| 游戏折扣日报 | LLM-driven | 2-5min | **需要调大** | Steam 爬取 + LLM 校验，当前 120s 不够 |
| 大兴笔试监控 | LLM-driven | 5-10s | 120s（默认） | 简单网页监控 |

**建议**：游戏折扣日报的 cron 任务需要增加系统级超时配置。如果 Agent 的定时系统不支持调整超时，考虑将 script 和 LLM 处理拆分。
