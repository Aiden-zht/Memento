# Cron 流水线架构设计原则

## 1. 模式选型

### 1.1 no_agent（脚本直跑）

```
cron tick → 执行 script → stdout 原样投递
```

**适用场景**：
- 纯数据收集/处理，无判断逻辑
- 固定格式输出（状态报告、日志摘要）
- 不需要对异常做条件判断

**优点**：零 LLM 成本、确定性强
**缺点**：不能处理条件分支、异常输出格式固定不可定制

**设计原则**：
1. no_agent 的 script 必须是幂等的（可重复运行不影响结果）
2. script 的 stdout 应该简洁有意义（≤200 字符为宜）
3. script 内部负责错误处理和日志，不要依赖 LLM 来做条件逻辑

### 1.2 LLM-driven（Agent 运行 prompt）

```
cron tick → 执行 script → 读取 stdout → LLM 分析 → 条件判断 → 后续动作
```

**适用场景**：
- 需要读取脚本输出并做条件判断
- 需要格式化输出（报告、邮件、通知）
- 多步骤 Pipeline（收集 → 校验 → 修复 → 发布）
- 异常处理需要人类可读的解释

**优点**：灵活、可处理复杂逻辑
**缺点**：消耗 token、执行时间长、超时风险高

**设计原则**：
1. LLM-driven 的 prompt 必须是自包含的（不依赖对话历史）
2. prompt 必须定义清晰的输入格式和输出格式
3. 每次 cron run 是独立会话，不能假设"上次成功"

### 1.3 混合模式（推荐）

```
脚本 A（no_agent）→ 产出数据文件
    ↓
脚本 B（LLM-driven）→ 读取 A 的产出 → 分析 → 决策 → 产出结果
    ↓
脚本 C（no_agent）→ 基于 B 的结果执行操作
```

**推荐模式**：数据收集用 no_agent，分析决策用 LLM-driven，操作执行用 no_agent。

## 2. 脚本包装规范

### 2.1 Wrapper 脚本模板

```bash
#!/bin/bash
set -euo pipefail

TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
cd /path/to/workdir || { echo "[$TIMESTAMP] ERROR: workdir not found"; exit 1; }

echo "[$TIMESTAMP] === Pipeline Start ==="

# 前置检查（代理、依赖、配置）
# ...

# 执行主脚本
python3 main.py 2>&1
EXIT_CODE=$?

# 结果报告
if [ $EXIT_CODE -eq 0 ]; then
    echo "[$TIMESTAMP] Pipeline completed successfully"
    # 产出状态文件
    echo "State file: output/state_$(date +%Y%m%d).json"
else
    echo "[$TIMESTAMP] Pipeline FAILED (exit $EXIT_CODE)"
    exit $EXIT_CODE
fi

echo "[$TIMESTAMP] === Pipeline End ==="
```

### 2.2 前置检查清单

脚本必须在主逻辑前检查：
1. **工作目录存在** — `cd /path || exit 1`
2. **代理可达** — 对外部 API 做可达性测试（curl 探测，超时 5s）
3. **配置/环境变量** — 检查必要的 .env 文件
4. **上游产出存在** — 如果是链式 job，检查上游 job 的产出文件

### 2.3 代理使用规范

**不要**在 wrapper 中重复设置代理环境变量（如 `https_proxy=socks5://...`），因为：
- 主脚本内部可能已经设置了代理（如 `cron_digest.py` 内部 `os.environ.setdefault`）
- 重复设置可能导致冲突（http proxy vs socks5 proxy）
- 主脚本内部的代理设置可能更精确

**正确做法**：
1. 主脚本（如 `cron_digest.py`）自己设置代理
2. Wrapper 只做可达性检查和结果报告
3. 如果主脚本确实需要代理但不支持配置，在 wrapper 中 `export` 设置

## 3. 依赖管理

### 3.1 技能依赖

Cron job 可以附加 skills（`skills: [...]`）。LLM-driven job 会在运行时自动加载这些 skill 的内容。

**注意**：skills 在知识库的 `references/` 中，不在 cron job 的 prompt 中。Skill 的内容会在每次 cron run 时注入到 prompt 开头，这会增加 token 消耗。

**优化**：只附加 job 实际需要的 skill，不要为了"可能有用的上下文"而堆砌 skill。

### 3.2 工作目录约定

- `workdir` 指定脚本执行目录
- `script` 路径相对于 `workdir` 解析（除非 script 是绝对路径）
- 如果 script 路径在 workdir 之外（如代理脚本库），直接使用绝对路径

### 3.3 文件产出约定

每个 cron job 的产出文件应存放在：
- **状态文件**：`output/state_YYYYMMDD.json`（JSON 格式，包含执行结果摘要）
- **数据文件**：`output/data_YYYYMMDD.json` 或 `.csv`
- **结果文件**：`output/result_YYYYMMDD.html` 或 `.md`
- **日志**：由 Agent 本地保存到工作区日志目录

**不要在 cron job 中直接写入 `references/` 目录**。运行数据（state、output、logs）与知识库文档分离。
