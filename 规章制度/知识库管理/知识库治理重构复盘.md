# 知识库治理重构复盘

> 本文是历史决策复盘，不是当前执行规范。
>
> 当前有效入口：
> - [[规章制度/知识库管理/知识库内容治理规范/index]]
> - [[规章制度/知识库管理/任务类型索引]]
> - [[AGENTS]]

## 一、本文定位

本文记录一次 KB 治理重构的背景、取舍和落地结果，用于帮助后续 Agent 理解：

- 为什么不再把 `provides` 当成唯一检索入口。
- 为什么移除 E10/E11 这类强管制 lint。
- 为什么把 `synopsis` 作为候选文件筛选字段。
- 为什么 `versions/spec_versions` 不再全库强制，而是只在硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现中按需使用。
- 为什么冷启动默认只保留 `AGENTS.md` + `任务类型索引.md`，其他治理正文按任务需要加载。

本文不用于指导日常任务执行。执行任务时，应先读 [[规章制度/知识库管理/任务类型索引]]，再按任务关键词全文搜索和 `synopsis` 筛选相关文件。

## 二、重构前的问题

### provides 管制层过重

`provides` 作为语义标签有价值，但围绕它叠加术语表、E10、E11、全库 tag 级版本同步后，维护成本超过收益。

典型问题：

- 大量 provides 标签只出现一次，强制登记收益低。
- Agent 不会稳定先查术语表，导致规范要求和实际行为脱节。
- 任务索引要求所有 provides 标签存在，会阻碍自然语言任务名和关键词使用。

### synopsis 缺失

Agent 搜到候选文件后，需要快速判断“这个文件是否该读”。只有 `title`、`tags`、`provides` 不够，必须有一句话说明文件用途。

### versions 全库强制不现实

对话 Agent 每次 session 从零开始，不需要长期版本表。大多数 skill/cron 应在执行时读取最新 KB；只有硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现才需要记录已验证版本。

### 本地实现运行时对齐没有闭环

早期规范只描述 KB 端版本变化，没有清楚规定本地 skill、cron prompt、脚本如何在执行时读取最新 KB、判断影响、必要时修改实现并验证。

### 冷启动默认加载过重

早期把 README、初始化规范、行为约束、多 Agent 协作规范和部分治理索引都描述为“所有 Agent 必读”。这会把“必须遵守”误写成“必须读完整正文”，导致普通任务冷启动时加载过多治理内容，增加 token 成本，也稀释当前任务真正需要的业务规范。

典型问题：

- `load: always` 文件过多，普通任务也会携带治理正文。
- “所有 Agent 必读”容易诱导 Agent 读取整个 L1/规章制度目录。
- README 和治理索引本应是导航，不应成为默认执行上下文。

## 三、最终决策

| 决策 | 当前状态 | 理由 |
|------|----------|------|
| `provides` 降级为辅助语义标签 | 已落地 | 仍可辅助检索，但不能替代全文搜索 |
| 任务入口改为任务索引 + 关键词全文搜索 | 已落地 | 更符合 Agent 实际行为 |
| `synopsis` 成为候选文件筛选字段 | 已落地 | 降低搜到但误读/漏读的概率 |
| 移除 E10/E11 | 已落地 | 避免把自然语言任务词误判成错误 |
| `versions` 改为按需使用 | 已落地 | 只对硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现有持续价值 |
| 本地实现运行时对齐规则写入 Agent 行为约束 | 已落地 | 规范变更后，skill/cron/脚本执行前读取最新 KB 并判断影响 |
| 冷启动默认路径收敛为 AGENTS + 任务类型索引 | 已落地 | 降低 token 成本；治理正文只在 KB 写入、初始化、协作、冲突或本地实现同步时加载 |

## 四、当前有效加载流程

```text
git pull
→ 读 AGENTS.md 和任务类型索引
→ 用关键词全文搜索候选文件
→ 读 frontmatter 的 synopsis/load/status
→ 按任务需要加载相关正文
→ 执行任务
```

已知 `provides` 标签时，可以辅助使用：

```bash
python3 scripts/provides-search.py --synopsis 标签1 标签2
```

但 `provides-search.py` 不是唯一入口；如果未命中，必须全文搜索兜底。

## 五、不应回滚的设计

| 不建议回滚项 | 原因 |
|--------------|------|
| 重建 provides 强术语表 | 维护成本高，Agent 不稳定使用 |
| 恢复 E10/E11 | 会增加噪声，阻碍自然语言任务索引 |
| 全库强制 tag 级 versions | 对对话 Agent 无实际价值 |
| 大规模合并普通参考文件 | 对 Agent 执行质量收益小 |

## 六、后续只按实际问题局部优化

后续优化只看一个问题：

> 这个改动能否降低 Agent 漏读规范、误读规范、跳过规范的概率？

能，就做；只是让目录更漂亮、标签更统一、报告更完整，但不改善执行质量，就不做。

## 七、与 Agent 原生能力的边界

后续治理不得把 Agent 当传统程序使用。Agent 原生支持全文搜索、自然语言理解、上下文推理、工具调用验证和 git history 追踪；KB 不应重复建设这些能力。

| 过度设计倾向 | 冲突点 | 推荐替代 |
|--------------|--------|----------|
| provides 受控词表 / 覆盖率 | 重复造搜索索引，且维护成本高 | 任务索引 + 全文搜索 + synopsis |
| E10/E11 复杂语义 lint | 用硬规则替代语义判断，噪声高 | 只保留结构 lint 和硬性断链检查 |
| 全库 tag 级 versions | 重复 git history，对对话 Agent 无价值 | 仅硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现维护 `spec_versions` |
| 多层目录索引和大规模合并 | 更适合人类浏览，不直接提升执行质量 | 高频任务入口 + BLOCKING 规则 |
| 所有治理正文默认必读 | 把“必须遵守”误当成“必须加载全文”，增加 token 成本 | `AGENTS.md` + 任务索引冷启动，其他正文按任务需要加载 |

用户当前优化取向：务实、简化、减少噪声；优先解决 Agent 漏读/误读/不执行规范的问题，不再为了体系完整性继续扩展治理机制。
