# 知识库治理重构复盘

> 本文是历史决策复盘，不是当前执行规范。
>
> 当前有效入口：
> - [[规章制度/知识库管理/知识库内容治理规范/index]]
> - [[规章制度/知识库管理/任务类型索引]]
> - [[AGENTS]]

## 一、本文定位

本文记录一次 KB 治理重构的背景、取舍和落地结果，用于帮助后续 Agent 理解：

- 为什么不再把 `provides` 当成唯一检索入口。
- 为什么移除 E10/E11 这类强管制 lint。
- 为什么把 `synopsis` 作为候选文件筛选字段。
- 为什么 `versions/spec_versions` 不再全库强制，而是只在硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现中按需使用。
- 为什么冷启动默认只保留 `AGENTS.md` + `任务类型索引.md`，其他治理正文按任务需要加载。

本文不用于指导日常任务执行。执行任务时，应先读 [[规章制度/知识库管理/任务类型索引]]，再按任务关键词全文搜索和 `synopsis` 筛选相关文件。

## 二、重构前的问题

### provides 管制层过重

`provides` 作为语义标签有价值，但围绕它叠加术语表、E10、E11、全库 tag 级版本同步后，维护成本超过收益。

典型问题：

- 大量 provides 标签只出现一次，强制登记收益低。
- Agent 不会稳定先查术语表，导致规范要求和实际行为脱节。
- 任务索引要求所有 provides 标签存在，会阻碍自然语言任务名和关键词使用。

### synopsis 缺失

Agent 搜到候选文件后，需要快速判断“这个文件是否该读”。只有 `title`、`tags`、`provides` 不够，必须有一句话说明文件用途。

### versions 全库强制不现实

对话 Agent 每次 session 从零开始，不需要长期版本表。大多数 skill/cron 应在执行时读取最新 KB；只有硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现才需要记录已验证版本。

### 本地实现运行时对齐没有闭环

早期规范只描述 KB 端版本变化，没有清楚规定本地 skill、cron prompt、脚本如何在执行时读取最新 KB、判断影响、必要时修改实现并验证。

### 冷启动默认加载过重

早期把 README、初始化规范、行为约束、多 Agent 协作规范和部分治理索引都描述为“所有 Agent 必读”。这会把“必须遵守”误写成“必须读完整正文”，导致普通任务冷启动时加载过多治理内容，增加 token 成本，也稀释当前任务真正需要的业务规范。

典型问题：

- `load: always` 文件过多，普通任务也会携带治理正文。
- “所有 Agent 必读”容易诱导 Agent 读取整个 L1/规章制度目录。
- README 和治理索引本应是导航，不应成为默认执行上下文。

## 三、最终决策

| 决策 | 当前状态 | 理由 |
|------|----------|------|
| `provides` 降级为辅助语义标签 | 已落地 | 仍可辅助检索，但不能替代全文搜索 |
| 任务入口改为任务索引 + 关键词全文搜索 | 已落地 | 更符合 Agent 实际行为 |
| `synopsis` 成为候选文件筛选字段 | 已落地 | 降低搜到但误读/漏读的概率 |
| 移除 E10/E11 | 已落地 | 避免把自然语言任务词误判成错误 |
| `versions` 改为按需使用 | 已落地 | 只对硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现有持续价值 |
| 本地实现运行时对齐规则写入 Agent 行为约束 | 已落地 | 规范变更后，skill/cron/脚本执行前读取最新 KB 并判断影响 |
| 冷启动默认路径收敛为 AGENTS + 任务类型索引 | 已落地 | 降低 token 成本；治理正文只在 KB 写入、初始化、协作、冲突或本地实现同步时加载 |

## 四、当前有效加载流程

```text
git pull
→ 读 AGENTS.md 和任务类型索引
→ 用关键词全文搜索候选文件
→ 读 frontmatter 的 synopsis/load/status
→ 按任务需要加载相关正文
→ 执行任务
```

已知 `provides` 标签时，可以辅助使用：

```bash
python3 scripts/provides-search.py --synopsis 标签1 标签2
```

但 `provides-search.py` 不是唯一入口；如果未命中，必须全文搜索兜底。

## 五、不应回滚的设计

| 不建议回滚项 | 原因 |
|--------------|------|
| 重建 provides 强术语表 | 维护成本高，Agent 不稳定使用 |
| 恢复 E10/E11 | 会增加噪声，阻碍自然语言任务索引 |
| 全库强制 tag 级 versions | 对对话 Agent 无实际价值 |
| 大规模合并普通参考文件 | 对 Agent 执行质量收益小 |

## 六、后续只按实际问题局部优化

后续优化只看一个问题：

> 这个改动能否降低 Agent 漏读规范、误读规范、跳过规范的概率？

能，就做；只是让目录更漂亮、标签更统一、报告更完整，但不改善执行质量，就不做。

## 七、与 Agent 原生能力的边界

后续治理不得把 Agent 当传统程序使用。Agent 原生支持全文搜索、自然语言理解、上下文推理、工具调用验证和 git history 追踪；KB 不应重复建设这些能力。

| 过度设计倾向 | 冲突点 | 推荐替代 |
|--------------|--------|----------|
| provides 受控词表 / 覆盖率 | 重复造搜索索引，且维护成本高 | 任务索引 + 全文搜索 + synopsis |
| E10/E11 复杂语义 lint | 用硬规则替代语义判断，噪声高 | 只保留结构 lint 和硬性断链检查 |
| 全库 tag 级 versions | 重复 git history，对对话 Agent 无价值 | 仅硬编码脚本、长期 cron 状态追踪、无法运行时加载 KB 的实现维护 `spec_versions` |
| 多层目录索引和大规模合并 | 更适合人类浏览，不直接提升执行质量 | 高频任务入口 + BLOCKING 规则 |
| 所有治理正文默认必读 | 把“必须遵守”误当成“必须加载全文”，增加 token 成本 | `AGENTS.md` + 任务索引冷启动，其他正文按任务需要加载 |

用户当前优化取向：务实、简化、减少噪声；优先解决 Agent 漏读/误读/不执行规范的问题，不再为了体系完整性继续扩展治理机制。

## 八、重大治理裁定必须自动写入复盘

当一次 KB 维护或圆桌裁定改变目录模型、入口权威链、加载策略、执行层闭环、公开版边界或反过度治理原则时，Agent 不需要再等待用户额外要求，应自动把“为什么这样设计”追加到本文。

写入边界：本文只记录历史决策背景、被否决方案、最终裁定、当前有效入口和不应回滚项；当前执行规则仍以 [[规章制度/知识库管理/知识库内容治理规范/index]] 及其子规范为准。

不写入：普通规则微调、修错字、脚本 bug、一次性圆桌意见、项目业务规则、执行日志、commit 细节。

## 九、七类目录与入口权威链裁定

### 背景

深度圆桌审计确认：基础 lint/self-check/audit 全绿不代表治理层没有语义漂移。主要风险不是断链，而是旧目录名、旧架构词、README 规则源漂移和执行层同步不可见，可能导致 Agent 搜错、落错或迁移错。

### 被否决方案

| 方案 | 否决原因 |
|------|----------|
| 恢复 `packages/业务包/specs/业务` 作为正式入口 | 增加解释成本、路由成本和误落库风险 |
| README 承载规则权威 | 会形成 AGENTS/任务索引之外的第二规则源 |
| 每次普通任务全量扫描 skill/cron/script | 成本高，且不符合 KB 只颁布规则的边界 |
| 新增重型 manifest、受控词表、全库版本数据库 | 让 KB 更像数据库，不能明显降低 Agent 漏读/误读概率 |
| 全库 always-load | 增加 token 成本，稀释当前任务需要的规范 |

### 最终裁定

| 决策 | 状态 | 理由 |
|------|------|------|
| 固化七类正式目录：规章制度、产物规范、专业知识、素材库、项目知识、用户资料、inbox | 已落地 | 对普通用户更直观，对 Agent 更可审计 |
| Agent 权威链为 AGENTS.md → 任务能力索引 → 任务类型索引 → index/synopsis → 按需正文 | 已落地 | 降低冷启动成本并避免 README 成为规则源 |
| README 降级为人类介绍 / Quickstart / 维护者参考 | 已落地 | README 不承载新规则，只说明如何开始 |
| 规则变更时触发执行层最小只读验收 | 已落地 | KB 不管理实现，但必须防止旧规则仍在生产执行层运行 |
| 公开版同步框架变化，私有项目知识、用户资料、素材和 prompt 不同步 | 已落地 | 保持公开版框架可复用且无私有内容 |

### 当前有效入口

- [[AGENTS]]
- [[规章制度/知识库管理/任务能力索引]]
- [[规章制度/知识库管理/任务类型索引]]
- [[规章制度/知识库管理/知识库内容治理规范/04-目录分类]]
- [[规章制度/知识库管理/知识库内容治理规范/07-Agent行为约束]]

### 不应回滚

- 不恢复 `packages/业务包/specs/业务` 为正式入口。
- 不让 README 成为规则权威源。
- 不把执行层资产写进 KB 法律。
- 不把所有普通任务升级为执行层全量扫描。
- 不为体系完整性新增重型治理机制；只做能降低 Agent 漏读、误读、跳过规范概率的改动。



## 十一、2026-06-15 封版前圆桌裁定：入口权威与项目知识落点

背景：全库 deep/full 圆桌审计认为 KB 无 P0，但封版前存在三类 P1：入口元数据异常、BLOCKING 双权威、10/12 双入口、项目知识默认落点不唯一、执行层闭环未实证。

最终裁定：

- `任务类型索引` 是唯一任务路由与 BLOCKING 执行入口。
- `强制规则索引` 降级为 archived 审计摘要，不进入普通冷启动链，不承载平行 active 权威。
- `12-项目任务知识接入设计` 是当前项目/长期任务接入唯一权威；`10-新业务接入流程` 降级为 deprecated 转接页。
- `项目知识/<项目>/` 默认位于 Memento 仓库内；外部项目目录只存代码、运行状态和产物，除非用户明确指定外部项目知识源。
- `load: always` 表示入口元数据应易发现，不等于普通任务 all-load 全文读取。

不应回滚：

- 不恢复 `packages`、`业务包`、`specs` 或旧业务目录为正式入口。
- 不把 README 升级为规则权威源。
- 不新增重 manifest、registry、全库版本数据库或受控词表。
- 不把全库深度圆桌审计常态化。


## 十二、封版实现功能清单与后续方向

### 当前已经实现的功能

- 冷启动入口：`AGENTS.md → 任务能力索引 → 任务类型索引 → index/synopsis → 按需正文`。
- 任务能力组织：读库、写库、消化 inbox、健康检查、存废审计、迁移重构、执行层对齐。
- 结构检查工具：`self-check.sh` 覆盖黑名单、废弃引用、索引、深度、Git、skills、膨胀、入口。
- 内容格式工具：`lint-knowledge-base.sh` 覆盖 frontmatter、Obsidian YAML 分隔符、误加管道符、wikilink、version/changelog、文件名。
- Agent 可用性审计：`audit-agent-usability.py` 覆盖模板泄漏、非 active 入口、占位链接、hook 缺失。
- provides 辅助定位：`provides-search.py --synopsis` 服务 skill/cron 固定依赖，不作为唯一入口。
- 提交门禁：`install-hooks.sh` / `pre-commit` / `safe-commit.sh` 支持提交前检查。
- 项目任务知识：长期项目规则和事实默认进入 `项目知识/<项目>/`，外部项目目录不作为默认规则权威。
- 执行层闭环：production skill 通过 `requires_provides` + `kb_refresh_policy: runtime` 运行时读取 KB；规则变化后需要只读扫描 skill/cron/script/SOUL/prompt。
- 公开版同步：私有框架变更可经 plan/apply/desensitize/verify/push/mark-synced 同步到公开 Memento。

### 接下来优先实现

1. 普通用户入口体验：把“用户怎么对 Agent 说”写得更清楚，减少人理解脚本的负担。
2. 执行层对齐自动报告：把 skill/cron/script/SOUL/prompt 的旧词扫描结果固定成一份可重复的只读报告。
3. 公开版最小示例：补一个不含私有业务的 `项目知识/<your-project>/` 示例，让新用户理解项目任务知识。
4. L3 新 Agent 验收：定期用零记忆 Agent 跑一次读库/写库/健康检查/执行层对齐样例，验证不是只有当前 Agent 会用。

### 当前设计宗旨

Memento 不是脚本集合，也不是数据库；它是给 Agent 使用的知识库治理框架。核心宗旨是：

- KB 只颁布规则，不执行规则；执行由 Agent、skill、cron、script 完成。
- 任务入口优先，不 all-load；普通任务只读与当前任务相关的正文。
- 全文搜索和 Agent 语义理解是主能力，provides 只做固定依赖辅助。
- 目录和文件必须可审计，但不为形式整洁制造重治理。
- 私有业务内容与通用框架分离；能开源的是治理框架和工具，不是用户资料、项目事实和运行资产。
- 每次规则变化都要考虑执行层是否继续按旧规则运行。
