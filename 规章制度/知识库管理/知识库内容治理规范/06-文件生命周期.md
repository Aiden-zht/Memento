# 文件生命周期

## 6.1 创建

| 触发条件 | 操作 |
|----------|------|
| 新增规范/标准 | 创建文件，加入 index.md 索引 |
| 新增项目 | 创建项目文档目录和 index.md |
| 新增参考文档 | 创建文件，加入对应目录 |
| 人工审核通过的文章 | 存入 few-shot 示例库 |
| 新增平台骨架 | 创建 `status: scaffold` 的占位文件，待后续填充 |

**创建前检查**：
- [ ] 这个内容是否属于知识库（白名单）？
- [ ] 是否已有类似文件？避免重复
- [ ] 放在哪个目录？按[[规章制度/知识库管理/知识库内容治理规范/04-目录分类]]判断
- [ ] 是否需要更新 index.md 索引？

## 6.2 文件状态

知识库文件使用 `status` 字段标识当前状态：

| 状态 | 含义 | 使用场景 |
|------|------|----------|
| `active` | 活跃文档，内容有效 | 规范、参考、索引 |
| `scaffold` | 骨架/占位文件，内容待填充 | 新平台目录结构、待创作文档 |
| `deprecated` | 已废弃，不再使用 | 短期保留的替代说明或迁移提示 |

`template/scaffold/draft/deprecated` 默认不参与生产任务加载。`scaffold` 文件应包含清晰的 TODO 标记，表明该文件尚不可用；其索引也必须标记为 `status: scaffold`，不能伪装成 `active`。`deprecated` 文件不应长期保留；无工作流依赖时直接删除，历史由 git history 保留。

## 6.3 更新

| 触发条件 | 操作 |
|----------|------|
| 规则变化 | 更新对应规范文件 |
| 发现错误 | 立即修正 |
| 新增信息 | 追加到现有文件 |
| 内容过时 | 标记 deprecated 或更新 |

**更新后必须**：
- 更新 `date` 字段
- git commit 并 push

## 6.4 归档/废弃

| 触发条件 | 操作 |
|----------|------|
| 内容过时且无依赖 | 删除文件，依赖 git history 保留历史 |
| 功能废弃但需短期提示 | 保留原路径，标记 `status: deprecated`，正文指向替代文件 |
| 被新版本替代 | 更新引用到新文件；旧文件无依赖后删除 |

原则：不要建立长期 `archive/` 内容库。归档目录会增加 Agent 检索噪声；历史追溯交给 git history。

## 6.5 删除

**优先用于清理无价值、无工作流依赖、会误导 Agent 的内容。以下情况应删除：

| 情况 | 操作 |
|------|------|
| 误创建 | 删除并说明原因 |
| 包含敏感信息 | 立即删除并 git commit |
| 完全无价值或仅有历史意义 | 删除，历史由 git history 保留 |
| `archive/` 中的 deprecated 内容 | 删除，避免日常检索误读 |

**删除前必须**：确认没有其他文件引用它。

## 6.6 文件变更伴随动作矩阵

目的：任何 KB 文件变更，都必须先判断“这个文件在体系中扮演什么角色”，再执行对应伴随动作。不要把伴随动作写散到每个文件里；统一按本矩阵判断，新增业务域时只补充域内影响项。

### 6.6.1 基础规则

| 变更类型 | 必须检查/修改 | 验证方式 |
|----------|---------------|----------|
| 新增普通文件 | frontmatter、`synopsis`、所在目录 `index.md` | lint；确认 index 有入链；必要时跑 Agent 可用性审计 |
| 新增目录 | 目录 `index.md`、上级目录 `index.md` | Obsidian 审计；确认不依赖目录 fallback |
| 修改正文内容 | 判断是否实质性规则变化；必要时更新 `version/changelog` | lint；读 changelog 是否能说明影响 |
| 修改规范/流程/检查项 | `version/changelog`；相关任务入口；相关 skill/cron/script 运行时加载入口 | lint；按 7.6 判断是否影响本地实现 |
| 修改 frontmatter | YAML 可解析；`load/status/synopsis/provides` 语义仍准确 | lint；必要时跑 provides-search |
| 修改 `synopsis` | 确认能帮助 Agent 判断“何时该读” | 搜索候选文件时读前 20 行验证 |
| 重命名/移动文件 | 全库 wiki-link、原目录 index、新目录 index、上级 index | 搜索旧路径；Obsidian 审计 `BAD_TARGETS 0` |
| 删除文件 | 搜索入链；更新 index；确认无工作流依赖 | 搜索文件名/路径；lint；Obsidian 审计 |
| 拆分文件 | 保留权威入口；新文件有 frontmatter；旧引用改到新入口或具体子文件 | lint；抽查任务入口仍能找到规范 |
| 合并文件 | 合并后文件更新 `version/changelog`；删除重复旧文件；更新所有引用 | 搜索旧路径；确认活动区无 orphan |
| 标记 deprecated | 正文写明替代文件；不长期保留；上游引用改到替代文件 | 搜索入链；确认没有新任务继续引用 deprecated |
| 修改 index | 只链接直接子目录 `/index` 和直接子文件；不用 `|显示文本`；active index 不应无提示指向 draft/scaffold/deprecated | Obsidian 审计 `PIPE_LINKS 0`、`DIR_FALLBACK 0`；`python3 scripts/audit-agent-usability.py` |

### 6.6.2 角色化影响判断

先判断文件角色，再追加检查：

| 文件角色 | 追加检查 |
|----------|----------|
| 根入口 / 冷启动入口 | 同步 `README.md`、`AGENTS.md`、根 `index.md` 中相互引用和启动流程 |
| 任务入口 | 同步 [[规章制度/知识库管理/任务类型索引]]，确保任务关键词和强制规则摘要仍准确 |
| 治理规范 | 同步治理规范索引、读取规范、新 Agent 初始化、相关复盘文档 |
| 业务规范 | 检查对应 workflow、质量检查、模板、风格库、项目文档是否受影响 |
| 质量/校验规范 | 检查 validator skill、Agent B 检查项、KPI/审核标记是否受影响 |
| 发布/API 规范 | 检查 cron prompt、发布脚本、环境变量说明、dry-run 验证步骤 |
| 模板/风格库 | 检查生成器、content generator、示例、反模式、Agent A 使用指南；模板文件必须 `load: template` + `status: scaffold` |
| 项目文档 | 检查项目入口 index、运行脚本、环境变量、输出路径是否一致 |
| 知识参考 | 通常只更新自身和 index；除非被任务入口或脚本硬编码引用 |
| 自建 skill/cron/script 依赖文件 | 按 [[规章制度/知识库管理/知识库内容治理规范/07-Agent行为约束#7.6-本地实现运行时规范对齐契约]] 判断是否需要改实现 |

### 6.6.3 可扩展规则

新增业务域或平台时，必须在该业务域的 `index.md` 或接入文档中声明“域内影响项”，但不要复制全局矩阵。

域内影响项只写本域特有依赖，例如：

```markdown
## 变更影响项

- 修改发布流程：检查 API 手册、发布脚本、cron prompt。
- 修改质量检查：检查 validator、KPI、审核标记。
- 修改文章模板：检查生成器、风格库、示例文章。
```

原则：

- 全局动作看本矩阵。
- 业务特有动作写在业务域入口或接入文档。
- 不给每个文件单独维护“变更声明”，避免知识库扩大后形成重复维护。
- 新增文件类型时，优先补充本矩阵；新增业务特例时，补充对应业务域入口。

### 6.6.4 最小执行顺序

1. 判断变更类型。
2. 判断文件角色。
3. 查本矩阵和业务域影响项。
4. 修改必要文件。
5. 运行 lint、Agent 可用性审计和必要的 Obsidian 审计。
6. commit + push。


## 6.7 回滚

Agent 改错内容、commit 并 push 后，按以下流程撤销。

### 6.7.1 回滚时机

以下情况应立即回滚：

| 情况 | 示例 |
|------|------|
| 写入了错误的规则 | 阈值写错、流程步骤写反、约束条件遗漏 |
| 删除了仍被引用的文件 | 入链未清就删了 |
| 改错了 frontmatter | `load: never`、provides 标签被误删 |
| 引入了违禁内容 | `.json`、`.html`、API key 等 |
| 语法错误导致 lint 不过 | 但 lint 没过 hooks 应该已拦截，此条为兜底 |

以下情况**不需要**回滚，正常再改一次即可：

| 情况 | 原因 |
|------|------|
| 文字澄清/措辞调整 | 不改变规则含义 |
| 补充说明/示例 | 新增内容，不破坏已有 |
| synopsis 微调 | 不影响 Agent 行为 |

### 6.7.2 回滚操作

```bash
# 1. 找到需要回滚的 commit
git log --oneline -10

# 2. 回滚（推荐用 revert，保留历史）
git revert <commit_hash>

# 如果是一连串多个 commit，逐个 revert 或:
git revert <oldest>..<newest>

# 3. 回滚后 lint
bash scripts/lint-knowledge-base.sh

# 4. 推送
git push origin main
```

### 6.7.3 回滚后的连带检查

回滚不只是撤销 git 历史。必须检查：

1. **入链完整** — 被回滚的文件如果被其他文件引用，确认引用路径仍正确
2. **索引同步** — 目录 index.md 是否仍指向正确文件
3. **provides 标签** — 回滚前后 provides 标签有变化？有则需重新验证依赖该标签的 skill
4. **下游通知** — 如果修正了一个已被其他 Agent 读取过的错误规则，应提醒相关 Agent 重新加载 KB

检查命令：

```bash
# 检查入链
search_files pattern="<被修改的文件名>" target="content"

# 检查 provides 标签影响
python3 scripts/provides-search.py --synopsis <受影响的标签>

# 整体健康
bash scripts/self-check.sh
```

### 6.7.4 回滚 vs 向前修复

优先**向前修复**（再 commit 一次改正），仅在以下情况用回滚：
- 错误涉及多个不相关的文件，逐一修太慢
- 错误已被其他 Agent 读取并据此执行了错误操作（回滚 + 通知）
- 错误 commit 是一个有害的快照，前进修复风险大
