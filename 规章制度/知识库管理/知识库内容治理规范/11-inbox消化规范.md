# inbox 消化规范

Agent 发现 `inbox/` 中有文件时，按此流程处理。

## 0. 核心原则

- **inbox 是投递口，不是入库承诺。**
- **先评审，后入库。**
- 只有具备长期复用价值、且属于 KB 白名单的内容才写入 KB。
- 低置信度提取结果不得自动入库。
- 不确定是否应入库时，先在对话中给出评审表，不直接写 KB。

## 1. 扫描输入

扫描 `inbox/` 下除 `README.md` 外的全部文件，不限于 `.md`：

```bash
find inbox -maxdepth 1 -type f ! -name README.md -print
```

按文件名、扩展名、大小先做输入清单。

## 2. 对话框提示

用户可能不会看 `README.md` 或 `inbox/README.md`。关键边界必须由 Agent 在对话中主动提示。

触发条件：

- 用户说“消化 inbox”；
- inbox 中存在非 Markdown 文件；
- inbox 中存在疑似临时材料、组织内部材料、政策/法规原文、考试/评估材料；
- Agent 判断某文件可能“不入库”或“需要确认”。

提示保持极短：

```text
我先做 inbox 评审：这些文件不一定全部入库。我会先判断：是否值得长期保存、是否需要转换、应进知识库还是项目 specs、提取质量是否可靠。低置信度或临时材料不会自动写入 KB。
```

如果评审后发现高风险文件，输出决策表：

```text
文件 | 建议动作 | 原因
A.doc | 仅提取，不入库 | 临时材料，无长期复用价值
B.md | 入知识/xxx | 长期可参考
C.pdf | 待确认 | 提取质量低
```

普通、低风险、高质量 Markdown 可继续自动消化，不需要反复打断用户。

## 3. 识别格式

按格式分流：

| 类型 | 处理方式 |
|------|----------|
| `.md` / `.txt` | 直接读取并评审 |
| `.doc` / `.docx` / `.wps` / `.pdf` | 先转换为临时文本，再做质量验收 |
| 图片、音视频、压缩包 | 默认不入 KB，除非用户明确要求并给出文本化目标 |
| 其他未知格式 | 先报告，不自动入库 |

二进制文档转换出的临时文本不直接入库，必须经过第 6 节质量验收。

## 4. 入库价值判断

每个文件先判定为以下之一：

| 判定 | 动作 |
|------|------|
| 入库 | 长期复用、属于 KB 白名单 |
| 仅提取/总结 | 对当前用户有用，但无长期复用价值 |
| 转项目 specs | 属于具体项目业务规则 |
| 不处理/待确认 | 价值不明、敏感、质量不足、分类会新增大目录 |

判断标准：

- 未来 Agent 是否会复用？
- 是否属于 [[规章制度/知识库管理/知识库内容治理规范/02-存什么]] 的白名单？
- 是否触犯 [[规章制度/知识库管理/知识库内容治理规范/03-不存什么]]？
- 是否只是一次性材料、临时材料、运行产物或生成产物？
- 是否属于某个项目的业务规则，应该进入项目 `specs/`？

## 5. 分类边界判断

对每个确定要持久化的独立主题，按 [[规章制度/知识库管理/知识库内容治理规范/04-目录分类]] 判断归宿：

| 内容类型 | 归入 |
|---------|------|
| Agent 必须遵守的治理规范 | `规章制度/` |
| 跨领域可参考知识 | `知识/` |
| 项目业务规则 | 对应项目 `specs/` |
| 通用模板 | `_templates/` |
| 生成产物、临时材料、运行状态 | 不入 KB |

`规章制度/` 的“规章”指 Memento/Agent 必须遵守的治理规范，不是外部文件标题里的“条例、制度、规定、意见”。外部政策、法规、组织制度原文如有长期参考价值，默认归入 `知识/`；如无长期复用价值，不入库。

如果该主题在 KB 中已有相关目录，**并入已有目录**，不要新建。

## 6. 二进制文档提取验收

`.doc/.docx/.wps/.pdf` 等文件必须先转换为临时文本。转换后执行最低验收：

- 标题与原文件/内容相符。
- 首段可读。
- 末段完整。
- 无大段乱码、控制字符或异常符号。
- 字符数/段落数没有明显异常。
- 如多个工具输出差异明显，优先人工评审，不自动入库。

验收失败时：

- 不写入 KB。
- 保留原始文件。
- 向用户报告 blocker 或请求提供可读文本。

## 7. 判断是否拆分

读每个可用文本。如果包含多个毫不相关的主题（不同领域、不同受众、独立性强的段落），**必须拆分为多个独立文件**。

判断标准：

- 两个段落的标题没有层级关系 → 拆。
- 放在同一个 KB 文件里会让搜索命中时产生噪音 → 拆。
- 一个段落可以独立被引用、独立被更新 → 拆。

不要把互不相关的规范、技术参考和项目资料塞进同一个文件。

## 8. 补 frontmatter

每个新建文件必须包含：

```yaml
---
title: "标题"
date: "YYYY-MM-DD"
tags: [标签1, 标签2]
category: "路径"
load: on-demand
provides: [可搜索标签]
status: active
synopsis: "一句话描述，帮助 Agent 快速判断是否该读。"
version: 1
changelog: "从 inbox 消化入库"
---
```

## 9. 创建文件 + 更新索引

- 创建 `.md` 文件到目标目录。
- 如果目标目录没有 `index.md`，新建。
- 更新目标目录 `index.md`。
- 更新上级目录 `index.md`（如果新增了目录）。
- 更新根 `index.md`（如果新增了二级目录）。

## 10. 清理策略

只有满足以下条件，才能删除 inbox 原始文件：

1. 已完成入库，或明确判定不入库；
2. 用户不要求保留；
3. 提取结果已验收；
4. git commit + push 成功；
5. `self-check` 通过。

如果只是“提取给用户看”，默认不删除原始文件，除非用户明确说不需要。

## 11. 提交与验证

```bash
bash scripts/lint-knowledge-base.sh
python3 scripts/audit-agent-usability.py
bash scripts/self-check.sh
bash scripts/safe-commit.sh "消化 inbox: <简述>"
```

完成后确认：

```bash
git status --short
```

输出为空，且远端已 push。
